# BPE 컨펌 툴 — 실제 작업 계획 (2026-11-13, 검증 반영판)

## 왜 하나

누크로 컨펌하는 것이 가장 편한데 누크를 많이 쓸 수 없게 됐다. 지금 BPE 피드백 탭은 원본 비교·채널 보기·
밝기 조절이 안 되고, 재생·이동·그리기가 불편하고, 작업 지시와 지난 수정 내용을 보기 어렵다.
**누크 없이 쓰는 누크 뷰어 + 샷그리드식 그림 메모 + 작업 비하인드**를 한 창에 담은 컨펌 전용 창을 새로 만든다.

- 화면 뼈대는 시안 A-3: 목록은 서랍, 위 막대는 누크식, 그리기 도구는 영상 위에 떠 있는 띠, 눈금 시간 막대,
  오른쪽에 작업 내용·지난 지적(읽기만)·메모·상태.
- 색·글씨·버튼 모양은 마지막 단계에서 다시 다듬는다. 지금 시안의 모양이 최종이 아니다.

## 가장 중요한 안전 장치

**지금 있는 피드백 탭은 그대로 둔다.** 새 컨펌 창은 따로 만들어 옆에 붙인다.
사용자가 "이제 옛 것 없애도 된다"고 할 때까지, 언제든 옛 화면으로 일할 수 있다.

**넣지 않기로 한 것:** 연속 보기(상태 누르면 자동으로 다음 샷), 컨펌 요약 한 장, 그레인·색 자동 판정, 지난 지적 체크 목록.
**나중으로 미룬 것:** 목록의 「다시 올라옴」 표시(지금은 버전 이력을 읽는 기능이 없음), 원본이 EXR·DPX 인 프로젝트.

## 검증한 방법과 결과

세 가지로 검증했다: ① 핵심 기술을 직접 시험, ② 지금 코드를 조사, ③ 다른 검토자가 계획을 반박.

**① 직접 시험**

| 확인한 것 | 결과 |
|---|---|
| 실제 MOV(1080p, 74프레임)를 메모리로 푸는 속도 | 8비트 0.8초·460MB, 16비트 1.1초·921MB → 샷을 열면 1~2초 안에 재생 가능 |
| BPE 가 쓰는 화면 라이브러리로 영상 계산 | 16비트 영상, 룩업, 차이, 게인·감마가 계산값과 일치(7개 시험 전부), 프레임 한 장 바꾸는 데 3.9ms. 새 라이브러리 없이 가능. **이 PC 한 대에서만 확인** |
| 원본 규격 | 예시 샷 원본은 3840×2076, 작업본은 1920×1080. 크기도 비율도 다름 |
| 편집본·원본·작업본 프레임 | 예시 샷 74 = 74 = 74, 어긋남 0 |

**② 코드 조사로 알게 된 것**

| 알게 된 것 | 계획에 주는 뜻 |
|---|---|
| 지금 영상 찾기는 내부 폴더 모양만 찾음. 외주 폴더(`comp\v002\`)는 샷그리드에 경로가 적혀 있을 때만 열림. 편집본 찾기는 아예 없음 | 지금 있는 찾기를 먼저 부르고, 그 위에 외주·편집본·원본 규칙을 덧붙인다. 옛 규칙 목록은 다른 기능도 같이 쓰므로 고치지 않는다 |
| 상태만 따로 바꾸는 길이 없음(노트 보낼 때만 같이 바뀜) | 메모가 비면 상태만 바꾸는 길을 새로 넣는다 |
| 영상 규격 읽기가 실패해도 가짜 값을 돌려줌 | 새 검사는 "모름"과 "다름"을 구분한다 |
| 피드백 화면은 매니저 잠금 뒤에 있음 | 새 창을 여는 버튼도 같은 자리에 둔다 |
| 룩업 파일 위치를 저장하는 곳이 없음 | 프로젝트별 룩업 파일을 고르고 기억하는 설정을 새로 넣는다 |
| 노트 만들기·그림 붙이기·지난 노트 읽기·버전 목록·컨펌 대기 목록은 이미 있음 | 그대로 다시 쓴다 |
| 피드백 화면·재생기·그리기에 자동 시험이 없음 | 새 창은 단계마다 자동 시험을 같이 만든다 |

**③ 반박 검증에서 나와 계획을 고친 것**

| 지적 | 고친 내용 |
|---|---|
| 노트는 보내는 순간 알림이 나가고 지우는 기능도 없어서 「되돌리기」가 실제로는 안 됨 | 「몇 초 뒤에 실제로 보냄, 그 전에 취소」로 바꿈 |
| 지금 보내기 흐름은 노트는 갔는데 상태 변경이 실패하면 "실패"로 떠서, 다시 누르면 노트가 두 번 감 | 새 창은 "노트 성공 / 상태 성공"을 따로 알려 주는 보내기를 새로 만들어 씀. 노트가 갔으면 다시 보내지 않고 상태만 다시 시도 |
| 외주 샷은 담당이 업체(그룹)라서 지금 방식으로는 노트 받는 사람이 비게 됨 | 외주 노트를 누가 받을지 정해야 함(남은 결정 1) |
| 원본과 작업본의 크기·비율·색 풀이 방식이 정해지지 않으면 차이 보기가 누크와 다른 그림을 보여 줌 | 색 풀이 방식을 고정해서 풀고, 크기가 다르면 경고와 맞춤 방식 고르기. 차이 보기는 규격이 같은 판끼리만 "정확"으로 표시. 룩업이 이미 입혀진 `_lut` 파일은 룩업을 또 씌우지 않음 |
| 자동 시험 서버에는 그래픽 장치가 없어 화면 계산 시험이 돌지 않음 | 계산식은 화면 없이 돌는 시험으로, 화면 계산 시험은 내 PC 필수 시험으로 나눔 |
| 2~6단계 동안 샷을 열 방법이 없음(목록은 뒤 단계) | 재생 바탕 단계에 "옛 피드백 화면에서 고른 샷을 새 창으로 열기"를 넣음 |
| 다른 PC·원격 접속·빌드에서 화면 계산이 되는지를 너무 늦게 확인함 | 맨 앞 단계로 옮김(작은 시험 창을 먼저 빌드해서 확인) |
| 메모리 한도가 숫자로 없음(16비트로 4개 판을 다 올리면 74프레임에 3.7GB) | 지금 버전만 전체를 올리고, 다른 판은 멈춘 프레임 주변만. 기본 한도 4GB, 넘으면 미리 올린 다음 샷 → 안 보는 판 순서로 버림 |
| 창을 닫아도 뒤에서 돌던 풀기 작업이 남을 수 있음 | 닫을 때 풀기 작업을 끝내고 메모리를 비움 |
| 프레임 번호 시작(1001) 규칙이 빠짐 | 지금 설정(기본 1001)을 그대로 쓰고, 번호가 찍힌 시험 영상으로 번호가 맞는지 자동 시험 |
| 한글 입력 상태에서 R·G·B 키가 안 먹을 수 있음 | 글자 말고 키 자리 기준으로 단축키 처리 |
| 목록은 500개까지만 읽어 와서 "컷 수 일치" 기준이 안 맞을 수 있음, 「다시 올라옴」은 읽을 기능이 없음 | 기준을 "같은 조건으로 조회한 수와 일치"로 바꾸고, 「다시 올라옴」은 나중으로 미룸 |
| 자동 시험이 실제 샷그리드에 닿을 수 있음 | 시험 중에는 실제 샷그리드 연결을 막는 장치를 먼저 넣음 |

## 작업 순서

각 단계는 **자동 시험 통과 → 실제 앱 화면을 그림·영상으로 보고 → 사용자 확인** 뒤에 다음으로 넘어간다.
단계마다 따로 커밋한다. 앱 코드는 단계를 시작하기 전에 다시 묻는다.

| 단계 | 만드는 것 | 끝났다는 기준 |
|---|---|---|
| 0 준비 | 새 작업 가지(브랜치). 지금 고치다 만 파일은 건드리지 않음. 시험 중 실제 샷그리드 연결을 막는 장치 | 기존 시험이 전부 통과하는 상태에서 시작 |
| 1 먼저 확인 | 영상 한 장을 화면 계산으로 띄우는 작은 시험 창 → 테스트 빌드 | 내 PC, 다른 팀 PC 한 대, 원격 접속 한 번에서 뜨는지 확인. 안 뜨는 환경이 있으면 여기서 방식을 다시 정함 (빌드는 승인 뒤) |
| 2 재료 찾기·검사 (화면 없음) | 샷 폴더에서 원본·편집본·버전 영상 찾기, 규격 읽기, 프레임 수·fps·해상도 판정 | 가짜 폴더 자동 시험 통과 + 실제 샷 3개(외주 모양·내부 모양·편집본 없는 샷)에서 결과가 눈으로 본 것과 같음 |
| 3 재생 바탕 | 컨펌 전용 창, 메모리 재생, 번갈아 보기, 프레임 이동, 눈금 시간 막대, 확대·끌기·맞춤, 옛 피드백 화면에서 "새 창으로 열기" | 실제 샷이 2초 안에 열림. 번호가 찍힌 시험 영상에서 화면 번호와 그림 번호가 일치. 같은 프레임을 ffmpeg 로 따로 뽑은 그림과 픽셀 값 일치. 창을 닫으면 메모리가 돌아옴 |
| 4 보기 도구 | 게인·감마, 채널, 차이, 룩업, 픽셀 값, 「보는 중」, 크기 경고·맞춤, 전체화면 | 직접 계산한 값과 화면 값 일치(자동 시험). 사용자가 아는 샷 하나를 누크와 나란히 놓고 눈으로 대조 |
| 5 그리기·글씨 | 표 7번 전부 | 창 크기·확대를 바꿔도 그림이 영상에 붙어 있음(자동 시험), 네모+글이 한 동작으로 끝남 |
| 6 메모·노트·상태 | 표 8·9번. 먼저 "부분 성공을 알려 주는 보내기"와 "몇 초 뒤 보냄·취소" | 가짜 샷그리드 자동 시험 통과(노트만 성공한 경우 포함). 실제 보내기는 사용자가 정한 시험용 샷 하나에서만, 사용자가 보는 앞에서 |
| 7 비하인드 | 표 10번 | 실제 샷 3개에서 워크 오더·지난 노트·붙은 그림이 샷그리드 화면과 같음 |
| 8 목록 | 표 11번 | 외주/내부 갈래의 컷 수가 같은 조건으로 샷그리드에서 조회한 수와 같음 |
| 9 마감 | 단축키 전부, 디자인 다듬기, 큰 글씨, 사용 안내, 옛 피드백 탭을 어떻게 할지 결정 | 사용자가 실제 컨펌 한 묶음을 이 창으로 해 보고 승인 |

순서의 이유: 방식이 통하는지부터 확인하고(1), 화면 없이 시험되는 것(2)을 먼저 만든다. 3~8단계는 전부 2·3단계 위에 올라간다.
4단계까지만 돼도 "누크 없이 번갈아·차이·밝기 보기"는 쓸 수 있다. 샷그리드에 쓰는 일은 6단계에만 있다.

## 위험과 대비

| 위험 | 대비 |
|---|---|
| 다른 PC·원격 접속에서 화면 계산이 안 됨 | 1단계에서 먼저 확인. 안 되면 옛 피드백 탭을 계속 쓸 수 있음 |
| 원본과 작업본이 크기·비율이 달라 차이 보기가 엉뚱하게 보임 | 경고 + 맞춤 고르기. "정확한 차이"는 같은 규격끼리만. 이 부분이 가장 먼저 틀어질 수 있는 곳이라 4단계에서 누크와 대조 |
| 긴 컷에서 메모리 부족 | 한도 4GB(설정에서 바꿈), 지금 버전만 전체, 나머지는 필요한 만큼만 |
| 프로젝트마다 폴더 모양이 달라 재료를 못 찾음 | 분명히 표시하고 직접 고르기 |
| 샷그리드에 잘못 보냄 | 6단계 전까지 쓰기 기능 없음. 몇 초 안에 취소. 노트 두 번 보내기 방지 |
| 빌드에서 앱이 안 뜸 | 1단계에서 테스트 빌드로 먼저 확인 |
| 화면 라이브러리 새 판이 나와 동작이 달라짐 | 지금 쓰는 판 범위에서 시험하고, 필요하면 판을 묶어 두는 것을 그때 제안 |

## 남은 결정

1. **외주 노트를 누가 받나** — 담당이 업체(그룹)라 지금은 받는 사람이 비게 된다. 업체 그룹에게 / 내부 담당자에게 / 둘 다.
2. **6단계 실제 보내기 시험에 쓸 샷.**
3. **룩업 파일 위치** — 프로젝트별 룩업(.cube)이 서버 어디에 있는지.
4. **노트에 붙는 그림** — 룩업 켠 평소 보기로 붙일지(게인·감마 올린 것은 안 구움).
5. **디자인 다듬기(9단계)에서 실제 프로그램 화면을 어떻게 참고할지** — 참고 화면을 직접 주실지, 제가 찾아봐도 되는지.
6. **1단계 테스트 빌드와 다른 PC 시험** — 어느 PC 에서 볼지.

## 약속 · 안 하는 것

- 앱 코드는 단계마다 먼저 묻고 수정. 빌드·배포는 승인 뒤에만.
- 서버(W:)는 읽기만. 샷그리드는 6단계 전까지 읽기만.
- 설정 파일 형식을 깨지 않음(새 항목만 더함). 누크 플러그인은 건드리지 않음.
- 옛 피드백 탭·AI 검사 버튼은 없애지 않음. 옛 탭에는 "새 창으로 열기" 버튼 하나만 더함.
- 지금 고치다 만 파일(`my_tasks_tab.py`, `windows_app_id.py`)과 섞지 않음.
- 새 라이브러리를 더하지 않음.
- 조사 중 보인 다른 문제(컨펌 대기 목록의 「샷 설명」이 늘 빈칸으로 보이는 것 등)는 이번에 고치지 않고, 따로 묻는다.
